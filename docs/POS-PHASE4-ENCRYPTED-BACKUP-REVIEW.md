## Version1 wire format — no cipher reimplementation

`BackupPackage.cs` uses platform PBKDF2/AES-GCM/IncrementalHash, no new runtime NuGet package.

- Header **40 bytes**: ASCII `A11BAK01` (8), random salt (16), independent random nonce prefix (8), little-endian signed plaintext ZIP length (8).
- Password KDF: PBKDF2-HMAC-SHA256, **600,000 fixed iterations**, 32-byte AES key. No attacker-selected iteration count or unbounded parameter. Password exact as entered; no trim/normalization. Random salt/prefix per package.
- Data: chunks up to **1 MiB**, each ciphertext followed by 16-byte GCM tag. Nonce = prefix8 + little-endian uint32 record index. AAD = entire header40 + the same index4. Bounded maximum means no nonce-counter wrap. Header, length and record position/order therefore participate in authentication.
- Final record: SHA256 of complete plaintext ZIP, encrypted as 32 bytes + 16-byte tag under next record index. Final record must authenticate, and checksum must match in constant time. Empty ZIP payload at codec level also has a final record (the service rejects an empty/non-ZIP archive).
- Exact encoded bytes = `40 + payloadLength + ceil(payloadLength / 1MiB) * 16 + 48`. Truncation, append, unsupported magic/version, invalid size and wrong password are rejected. Decrypted earlier chunks are **not a usable backup** until completion succeeds. Secret key/plain buffers are zeroed in finally; managed strings/GC/OS caches cannot be promised erased.
- Payload <= **32 GiB**. This is not unlimited storage or a promise that huge backups are practical on every disk. Password security still depends on password strength; offline guessing remains possible. A password holder can legitimately decrypt/rebuild a package: this is not DRM or protection from an administrator/password holder. Merely opening unchanged bytes is not detectable tampering.

## ZIP limits before use

EOCD/ZIP64 preflight before ZipArchive allocates central entries: one disk, bounded count **60,000**, central directory <= **128 MiB**, validated offsets/directory extent. Commented ordinary ZIP EOCD supported; unsupported/malformed extensions fail closed. Then inspect all central paths/declared lengths before decompression. Total expanded <=32 GiB; individual file <=8 GiB; manifest <=64 KiB; expansion ratio <=10,000:1. Count includes DB/manifest/directories. Writer checks source totals/count too. Actual streams have a bounded copy and must match declared expanded sizes.

Only exact `area11.db`, optional `area11-backup.txt` and `photos/...`; case-insensitive duplicate names rejected. Reject rooted/parent/dot/empty segments, backslashes, alternate-stream colons, control/Windows-invalid characters, trailing dot/space, reserved devices, symlink archive entries, excessive path/segment length. Existing photo links/junctions rejected during restore; nested source reparse-point photos are skipped and root links rejected. Archive/database rejection precedes live replacement. These are supported-format limits, not a general ZIP repair tool.

## Local storage / recovery caveats

- Credential and private staging live under the **current Windows user's profile**, separate from configured DB/photos/backups, outside backup payload. Default inherited profile ACL is relied upon; actual ACL/current-user/different-user behavior is **UNRUN**. A changed DB path requires password setup for that scope. A shared Windows login shares its DPAPI trust. Local admin/current-user malware is outside the threat model.
- Plain ZIP/SQLite/photo staging is needed to verify a large archive before applying it. Fresh operation-specific private directory; best-effort cleanup on success/failure. Crash, file lock, antivirus or deletion failure may leave private plaintext staging. Cleanup is not secure erasure; encrypted package protection does not encrypt the live DB, photo folder, swap file or disk. Do not advertise disk-at-rest encryption.
- SQLite snapshot is transactionally consistent, but photo files are copied separately and can change/disappear while backing up. There is no atomic DB+photo filesystem snapshot or global write quiescence. **Stop shop work before restore**; concurrent billing/other processes, power loss between DB/photo swaps and disk-failure recovery remain physical fault gates.
- Rotation only affects later packages. On a new PC/Windows account first set up a local backup password for its current-state safety, then select original .a11bak and enter its original password. Old source password and new local safety password can differ. Keep both safely; app login reset cannot recover a lost backup password. Never delete old backups before an encrypted backup plus genuinely isolated restore has been verified.
- Existing photo merge semantics retained: included photos overwrite/add matching files; absent photos are not treated as deletion commands. Database-only/zero-photo backup does not erase live pictures. Full safety captures existing supported photo files; rollback removes newly added files and reinstates prior ones best effort. Not a new all-files directory clone/transaction guarantee.
